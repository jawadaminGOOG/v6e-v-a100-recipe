The idle half of the host

Customers pay for that host CPU either way, then buy separate CPU nodes for their services. Our claim: GKE can fill the idle cores with those services, protect serving latency, and overflow the rest to N4D automatically.

Inside the host: G4 vs v6e

To scale, one tile per vCPU. vLLM owns 4 whole cores in L3 0; each backfill pod owns one whole core.

Exclusive cores isolate compute, not cache or memory. Each L3 slice is shared by its 7–8 cores, and memory bandwidth by the whole host (red dashes). That is where we measured the interference: memory-bandwidth-bound neighbours raised vLLM TTFT p99 by 124 %, integer neighbours by 6 % (slide 5). So the recipe keeps memory-heavy services off accelerator hosts.

How it works on GKE

vLLM keeps 8 vCPU, CPU services fill the rest, and GKE reacts when either demand changes.

  1. LLM traffic rises → request-rate metric → vLLM HPA adds a replica → GKE adds an accelerator node → waiting CPU pods land on its spare cores.
  2. CPU demand rises → pods that don't fit wait → overflow metric → overflow HPA → GKE adds an N4D node and runs them there.
  3. Guardrails keep serving safe: vLLM's cores are exclusive, memory-heavy services never land on accelerator hosts, only serving can use the GPU or TPU.

What it saves

Avoids $501/mo per G4 host and $445/mo per TPU v6e host of N4D spend

At the colo we measured (36 of 40 spare vCPU on G4, 32 of 36 on v6e), N4D and host both on 3-yr CUD: 34.7 % and 50 % of the host's own price.

Same GPU as AWS g7e.2xlarge, effectively $1.35/hr vs $1.45

G4 adds 40 vCPU and 116 GiB on the host. Put 90 % of them to work and its 3-yr price drops 6.9 % below AWS 3-yr No Upfront.

Spare = host vCPU − vLLM's 8 (G4 40, v6e 36). Light, typical and full = 25, 60 and 90 % of spare; N4D priced as n4d-standard-16 on the same purchase option as the host; 730 h/month. G4 in us-west8, v6e in us-east5, public list prices.
